# Data contract v1 — simulation → dashboard (DRAFT `1.0.0-draft`)

Status: draft for review · Written 2026-11-17 · Owner: simulation workstream · Consumer: frontend / visualization workstream
Machine-readable: `swiss/contract/schema/*.schema.json` (generated by `swiss/contract/schema_gen.py` from the data dictionary
`swiss/contract/variables.py`) · TypeScript: `web/src/lib/contract/` · Data: `web/public/bundle/sim/` (48-hour sample) and `web/public/bundle/sim_full/` (full year), see §9

This contract supersedes the draft field names in `frontend_agent_brief.md` §6.2. Every value in the sample comes from a real
CityLearn 3.3.0 rollout of the Phase A district; no number is typed in by hand.

## 1. Delivery and versioning
- Static JSON files under `/bundle/sim/`, read with `useSim`-style hooks (`web/src/lib/contract/index.ts`). No live API (owner decision).
- Every file carries `contract_version`. **Additive** changes (new optional field, new variable) bump the minor version;
  **breaking** changes (rename, unit change, removed field) bump the major version and are announced to the owner first.
  While the version ends in `-draft`, field names may still change after review.
- The manifest records the git commit, whether the tree was dirty, SHA-256 of every file and of every input.
  `swiss/tests/test_contract.py` fails when an input changed and the sample was not regenerated.

## 2. Files
| File | Content |
|---|---|
| `manifest.json` | Version, kind (`sample` or `full`), time axis, buildings, controllers, scenarios, run index, **variable dictionary**, situation tags and thresholds, units, consistency checks, hashes |
| `buildings.json` | Per building (keyed by id): identity, attributes and components, each with `value`, `unit`, `provenance`, `source_ids`, `available` |
| `components.json` | Phase-aware component registry (modeled vs not modeled, phase A/B/C) and the energy / signal / control flows between them |
| `conditions.json` | Shared per-step inputs: weather, tariff, relative carbon rank, local time, gap flags |
| `runs/<scenario>/<controller>.json` | One controller's per-step results for all buildings and the district, sparse situation tags, summary |
| `comparisons.json` | Each controller against the reference ("No control") over the file's `scope` (the sample window now), with the quantities that explain the difference |
| `comparisons_year.json` | The same structure over the **whole simulated year** (small: no per-step arrays). Use it for the Results page; check `scope.kind` before labelling |

## 3. Conventions (read before building anything)
**Time.** Step `i` of a run array is simulation step `scope.start_step + i`. Step 0 = 2022-12-31T23:00Z = 2023-01-01 00:00 local
(D-007). `conditions.json` uses the same indexing; `timestamps_utc` and `local_time` give the clock. A full run has 8,759
steps (CityLearn does not simulate the last hour) while inputs have 8,760: use the run length as the timeline length.

**Energy, not power.** Every series is **energy per step**. Mean power over a step is `kWh / (step_seconds / 3600)`
(`meanKw` in `units.ts`). At hourly steps the numbers coincide; at the 15-minute steps of Phase B they differ by a factor of 4.
Electricity (`kWh_el`) and heat (`kWh_th`) are always separate variables.

**Unavailable vs zero.** `null` means *not available / component absent*, a real zero is `0`. Series of a missing component
are JSON `null` as a whole (SFH-low has no hot-water tank, so all its `hw_tank_*` series and `hp_hw_to_tank_kwh_th` are `null`);
`buildings.json` marks the component `present: false`. Attributes that are not known carry `available: false`, `value: null`,
`provenance: null` and a reason. Do not render them as 0.

**Provenance.** `measured | derived | modeled | synthetic | assumed_parameter` (four data classes plus the assumed-parameter
badge). Classified by how a value was obtained. `provenance` can be a pair `{SFH, MFH}` when the class depends on the building type.
`source_ids` are registry IDs: open the audit card with `useNodeParam().open(id)`.

**Names.** Building ids are fixed (`SFH-mid`, not "SFH-medium"); the visible name is `buildings.<id>.display_name`.
`hw` stands for **"hot water and other heat-pump base load"** (CityLearn's `dhw`; D-014e). Always show the `label` from
`manifest.variables`, never the id. SFH-mid and SFH-high heat water electrically; that electricity is in `household_kwh_el`.

**Carbon.** Only `carbon_relative_rank` (percent of the year's hours with lower modeled intensity) and
`relative_carbon_change_pct` (change against the reference) exist. No absolute carbon value is exported, on purpose (D-013b, ISS-033).

**The district is a composite.** `manifest.district_note` must be shown wherever the six buildings appear together.

## 7. Situations (data-driven "What is happening?")
`situations.district` and `situations.buildings.<id>` map a tag to the steps (relative to `scope.start_step`) where it holds. A tag
that is absent never holds. Write explanatory text from tags **and** the values at that step, and claim a mechanism only when a
tag supports it (for example "stored heat is covering demand" only when `sh_tank_covers_demand` holds). Thresholds are in
`manifest.situation_thresholds`.

| Tag | Meaning |
|---|---|
| `cold_hour` | Outdoor temperature at or below the 10th percentile of the year (threshold in situation_thresholds.cold_temp_c). |
| `high_tariff` | High tariff tier. |
| `low_tariff` | Low tariff tier. |
| `district_daily_peak` | The hour with the highest district grid import of its local calendar day. |
| `sh_tank_charging` | Space-heating tank receives heat from the heat pump. |
| `sh_tank_discharging` | Space-heating tank delivers heat to the demand. |
| `sh_tank_idle` | Neither charging nor discharging. |
| `sh_tank_full` | Tank fill level at or above situation_thresholds.tank_full_soc. |
| `sh_tank_empty` | Tank fill level at or below situation_thresholds.tank_empty_soc. |
| `sh_tank_covers_demand` | The tank supplies at least situation_thresholds.storage_covers_demand_share of the space-heating demand (demand > 0). |
| `hw_tank_charging` | As sh_tank_charging, hot-water/base-load tank. |
| `hw_tank_discharging` | As sh_tank_discharging, hot-water/base-load tank. |
| `hw_tank_idle` | As sh_tank_idle. |
| `hw_tank_full` | As sh_tank_full. |
| `hw_tank_empty` | As sh_tank_empty. |
| `hw_tank_covers_demand` | As sh_tank_covers_demand, for the hot-water/base-load demand. |
| `hp_sh_near_capacity` | Space-heating heat-pump electricity at or above situation_thresholds.near_capacity_fraction of its nominal electrical power. |

## 8. Comparisons and what they explain
`comparisons.json` (scope: the sample window) and `comparisons_year.json` (scope: the whole year) share one structure; always read `scope.kind`
and label percent changes with it (a 48-hour change is not an annual result). Both compare each controller with the reference ("No control").
`metrics` hold value, reference, delta and percent for import (`kWh_el`), highest hour and mean daily peak (`kW_el`, 24-step blocks as in the KPI
table), cost (`CHF`), high-tariff import share, heat-pump electricity, tank losses and heat delivered from tanks. These are **district totals**
(energy-weighted). CityLearn's `kpi_*` columns are different: the unweighted mean of per-building ratios, so do not mix them.

`mechanisms` are **exact accounting identities** (tested). The demand is fixed, so a controller only changes the heat passing through the tanks:
- `extra_hp_electricity_kwh_el` = `electricity_from_tank_losses` + `electricity_from_stored_remainder` + `electricity_from_cop_timing`
  (heat lost in the tanks and heat still stored at the end of the scope, each converted at the charging COP, plus the effect of charging at a
  different COP than the one at the time the heat is used); also = `tank_charging_electricity` - `electricity_avoided_at_discharge`.
- cost delta = `cost_from_tariff_timing_chf` (negative = cheaper hours used) + `cost_from_extra_electricity_chf` (extra electricity bought at the charging price).
- `relative_carbon_change_pct` = `carbon_from_timing_pct` + `carbon_from_extra_electricity_pct`: same identity with the modeled carbon series, in percent of the
  reference, **relative only**.
- `tank_heat_in_kwh_th` - `tank_heat_out_kwh_th` - `stored_heat_change_kwh_th` = heat lost in the tanks (`extra_tank_loss_kwh_th`).
- `import_moved_out_of_high_tariff_kwh_el`, `peak_step_reference` / `peak_step` (when the highest hour occurs).
Say "because" only for what these identities show. They do not explain why a rule charges when it does, and they depend on the assumed tanks
(D-017a). See `docs/experiments/validation_reports/mechanism_check_phase_a.md` for the checked wording of the Phase A findings.

## 9. Sample and full-year bundles, regeneration
Two folders hold the same files with the same schema; only the length differs (`scope.n_steps`):
| Folder | `manifest.kind` | Steps | Size | Use |
|---|---|---|---|---|
| `web/public/bundle/sim/` | `sample` | 48 hours from local midnight of the coldest weekday of 2023 (Monday 2023-12-04, steps 8088-8135) | about 0.4 MB | development and tests |
| `web/public/bundle/sim_full/` | `full` | the whole simulated year, 8,759 steps (inputs 8,760) | about 57 MB raw (about 10 MB per run), about 15 MB gzipped | the real timeline; decision D-028 |
All six controllers are in both. The sample is an **exact slice** of the full year (tested): same values, same rounding. In the frontend pass the variant to the hooks
(`useRun("base", controller, "full")`); never hardcode a length, read `scope.n_steps` and `conditions.timestamps_utc`.
```bash
cl/bin/python -I swiss/contract/export_v1.py                                          # sample (about 5 minutes: six real full-year rollouts)
cl/bin/python -I swiss/contract/export_v1.py --full --out web/public/bundle/sim_full  # full year, same code and schema
cl/bin/python -I swiss/contract/schema_gen.py                                         # regenerate schemas after editing variables.py
```
```bash
PYTHONPATH=. cl/bin/python -m pytest swiss/tests/test_contract.py swiss/tests/test_contract_full.py -q
```
Regenerate both only when results or the contract change (about 57 MB of JSON per regeneration), on a clean committed tree so the manifests record `git_dirty: false`.

## 11. What the simulation does not provide (never display as zero)
Indoor temperature, comfort and unmet heat; number of floors; apartment-building floor area and residents; PV; batteries; EVs; absolute
carbon; real forecasts; any heat or electricity exchange between buildings.

## 12. Known caveats of the data
- Tank sizes, efficiency (0.95) and loss rate (0.3 %/h) are assumed parameters (D-017a); every controller difference depends on them (ISS-029, ISS-032).
- Heat demand is derived from electricity and its timing is unvalidated (ISS-028, ISS-030).
- The tariff is classified `measured` in the registry (a published price schedule, not a metered quantity); the dictionary says so in its description.
- `*_tank_loss_kwh_th` is exact by energy conservation (into tank - out of tank - change in stored heat) and includes round-trip and standby losses.
- `*_tank_action` is the command, not the executed flow.
- The sample's `generated.git_dirty` reflects the tree at export time; regenerate on a clean committed tree before publishing.
